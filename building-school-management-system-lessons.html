Building a School Management System: Lessons from a Real Project

Most of my client work is websites and stores, but SchoolOS was a different kind of project - a genuine software system, not just a site. Building it taught (or re-confirmed) some lessons worth sharing for anyone considering a similar custom system, whether for a school or any other multi-user operational tool.

What the system actually needed to do

A school management platform isn't one feature - it's several distinct systems that all need to work together: authentication with different roles (admin, teacher, student, parent), attendance tracking, a gradebook, fee payment processing, an admissions pipeline for new applicants, and staff payroll. Each of these is arguably its own small application; the real engineering challenge is making them share data cleanly without becoming a tangled mess.

Lesson 1: Role-based access has to be designed early, not bolted on

A teacher should see their own classes' grades but not payroll data. A parent should see their own child's attendance but not the whole school's. Retrofitting proper permission boundaries after building features "generically" is genuinely painful - deciding the role/permission model at the start, even in rough form, saves significant rework later.

Lesson 2: Payments need to be treated as their own subsystem

Integrating Stripe for fee payments isn't just "add a checkout button" - it means handling partial payments, payment failures, refunds, receipts, and reconciliation against what the school's admin actually expects to see in their records. Payment logic deserves disproportionate testing time relative to how simple it looks on the surface.

Lesson 3: PDF generation is trickier than it looks

Report cards need to be generated as clean, printable PDFs pulling live data (grades, attendance, teacher comments) into a consistent template. Getting PDF layout to render correctly and consistently - especially with dynamic-length content like teacher comments - took real iteration; it's a feature that looks simple in a spec document and isn't in practice.

Lesson 4: Admissions workflows need real state management

An application isn't just "submitted" or "not submitted" - it moves through stages (received, under review, interview scheduled, accepted/rejected, enrolled), and different staff need to see and act on different stages. Modeling this as an actual state machine, not just a status text field, made the admin experience far more reliable.

Lesson 5: Build it as a real product, not a one-off client site

Because a system like this has this many interconnected parts, treating it with proper software engineering practices - a real database schema with migrations, TypeScript for type safety across the growing codebase, structured API routes - paid off far more than it would on a simpler marketing site. The extra rigor upfront is what makes a system like this maintainable as features keep getting added.

Was Next.js and TypeScript the right call?

For a project this stateful and long-lived, yes - TypeScript's type-checking caught real bugs before they reached users, especially across a growing set of interconnected data models (students, classes, grades, payments, admissions all reference each other). This is a good example of when the extra structure genuinely earns its complexity, unlike a simple marketing site where the same tooling would be overkill (see our React vs plain JavaScript piece for that side of the tradeoff).

The takeaway for anyone considering a similar system

If you're evaluating whether your organization needs something like this built custom versus buying an existing SaaS product, the honest answer depends on how much your workflows differ from generic templates. If your needs are standard, an existing product is usually cheaper. If your workflows are genuinely specific to how your organization operates, custom development - done with the rigor described above - is often worth the investment.
